# ZigLED — Zigbee-controlled WS28xx LED controller on ESP32-C6

- **Author:** Gekkotron
- **Date:** 2026-08-28
- **Status:** Design approved; implementation plan pending

## 1. Purpose

Firmware for an ESP32-C6 that drives WS28xx addressable LED strips and matrices, controlled over Zigbee 3.0 and integrated into Home Assistant via Zigbee2MQTT. The device presents itself as a standard Zigbee light with an additional manufacturer-specific cluster for effect selection, speed, intensity, and palette. All effects are rendered locally on the device; Zigbee only carries user intent, never per-frame pixel data.

The project is a redesign — not a port — of an existing Arduino/FastLED prototype in this repo (`zb_ws2815_c6/zb_ws2815_c6.ino`). The prototype's external Zigbee contract, model/vendor strings, endpoint layout, and effect enumeration are all being replaced. The prototype remains in the repo as reference material for effect tuning (fire zones, phase-step scaling, HSV mode handling), not as a binary compatibility target. Devices flashed with the prototype must be re-paired after moving to ZigLED.

## 2. Non-goals

- **No WiFi.** WLED already occupies that niche; ZigLED is Zigbee-first.
- **No per-frame streaming over Zigbee.** ~250 kbps shared bandwidth makes it impractical. The coordinator selects *what* the device renders, not each frame.
- **No hardware / PCB design in this project.** Firmware only.
- **No OTA in v1.** ZCL cluster `0x0019` can be added later without breaking the external contract.
- **No color temperature (mireds).** The prototype's `ZigbeeColorDimmableLight` doesn't expose it and no downstream use case has been named. Can be added later by promoting to an Extended Color Light device type.

## 3. High-level architecture

- Language: **Zig**, wrapping ESP-IDF and ESP-Zigbee-SDK via `@cImport`.
- Build system: ESP-IDF component wrapping a Zig static library. Zig owns the app; ESP-IDF owns Wi-Fi radio init, RMT peripheral, NVS, FreeRTOS, and the Zigbee stack.
- Two FreeRTOS tasks:
  - **`zigbee_task`** — runs the ESP-Zigbee-SDK event loop. All ZCL attribute-write / command callbacks translate into typed `Command` messages posted to a FreeRTOS queue.
  - **`render_task`** — 60 Hz tick via `vTaskDelayUntil`. Owns the framebuffer, effect state, LED output driver, NVS debounce timer, and the BOOT button watcher.
- One command queue between them. No reverse channel in v1; attribute *reports* are generated by the Zigbee task from `state` on a timer.
- Rendering fully owns pixels — no locking on the hot path.

## 4. External Zigbee contract

Single endpoint, ZCL 3.0, device type **`0x010D` (Extended Color Light)**.

### 4.1 Standard server clusters

| Cluster | ID | Notes |
|---|---|---|
| Basic | `0x0000` | `ManufacturerName="Gekkotron"`, `ModelIdentifier="ZigLED-1"`, `PowerSource=DC`, `SWBuildID` = firmware version string. |
| Identify | `0x0003` | 2 Hz white flash blended at 50% over whatever is rendering. |
| Groups | `0x0004` | Standard, backed by ESP-Zigbee-SDK. |
| Scenes | `0x0005` | Standard, backed by ESP-Zigbee-SDK. |
| On/Off | `0x0006` | `StartUpOnOff=0xFF` (restore previous state) — our NVS restore satisfies this. |
| Level Control | `0x0008` | `CurrentLevel` 1–254. Level transitions are rendered by the render task, not the Zigbee task. |
| Color Control | `0x0300` | Advertise xy mode only (`CurrentX`, `CurrentY`). No Hue/Sat, no mireds. Rationale: xy maps cleanly to the linear color pipeline; the Arduino prototype needed dual HSV+RGB callbacks only because the Espressif Arduino library exposes them separately — at the raw ESP-Zigbee-SDK level we only handle xy attribute writes. |

### 4.2 Manufacturer-specific cluster `0xFC01`

Manufacturer code `0x1337` (placeholder — private-range, documented as such; no CSA registration needed for personal use).

| Attribute | ID | Type | Access | Meaning |
|---|---|---|---|---|
| `EffectId` | `0x0000` | `uint16` | RW, reportable | See §6 for the roster. |
| `EffectSpeed` | `0x0001` | `uint8` | RW, reportable | 0–255, mapped per-effect. |
| `EffectIntensity` | `0x0002` | `uint8` | RW, reportable | 0–255. Ignored by effects that don't use it. |
| `PaletteId` | `0x0003` | `uint8` | RW, reportable | `0` = "use commanded color from ColorControl"; `1..N` = built-in palettes. |
| `EffectCount` | `0x0004` | `uint16` | R | Number of registered effects in this build. Comptime-computed. |
| `PixelCount` | `0x0006` | `uint16` | R, reportable | Total LEDs on this device across all output pins. Comptime constant. |
| `LayoutKind` | `0x0007` | `enum8` | R | `0`=strip, `1`=serpentine matrix, `2`=multi-panel, `3`=custom. |
| `LayoutWidth` | `0x0008` | `uint16` | R | Pixels per row for matrix/multi-panel; `0` for strip/custom. |
| `LayoutHeight` | `0x0009` | `uint16` | R | Rows for matrix/multi-panel; `0` for strip/custom. |
| `SchemaVersion` | `0xFFFD` | `uint16` | R | Cluster schema version, `= 1`. Bumped only on breaking cluster changes. |

No manufacturer-specific commands in v1 — every user action is an attribute write.

### 4.3 Reporting

Default reporting is configured on: `OnOff.OnOff`, `LevelControl.CurrentLevel`, `ColorControl.CurrentX/Y`, and all four RW mfg attributes. Min 1 s, max 60 s, sensible reportable change per attribute. `PixelCount` and layout attributes report on change only.

### 4.4 Z2M external converter

Ships in the repo as `z2m/gekkotron_zigled.mjs`:

- Fingerprints on `modelID="ZigLED-1"` + `manufacturerName="Gekkotron"`.
- Standard clusters → `zigbee-herdsman-converters` `modernExtend` (`light`, `identify`), yielding all default color-bulb UX.
- Mfg cluster `0xFC01` → exposes:
  - `effect` as `enum` (built from a hardcoded list synced with the firmware's registration table; `EffectCount` is a runtime sanity check).
  - `effect_speed`, `effect_intensity`, `palette` as `numeric` sliders.
  - `pixel_count`, `layout_kind`, `layout_width`, `layout_height` as read-only info entities.

The converter is a one-file drop into Z2M's `external_converters:`. No Z2M fork required.

## 5. LED render pipeline

### 5.1 Frame cadence

Render task ticks at fixed 60 Hz using `vTaskDelayUntil`. Each tick, in order:

1. Drain command queue (bounded ≤ 16 commands per tick).
2. Advance effect state (`dt = 1/60 s`, monotonic clock).
3. Call `effect_engine.render(state, t, frame_buffer)` — pure function.
4. Post-processing (see §5.3).
5. Push to `led_output` (RMT DMA transmit).
6. Debounce NVS write if state dirty (see §7).
7. Poll BOOT button (see §7.3).

Frames that overrun 16.6 ms skip the *sleep* but not the *work* — animations slow instead of tearing. A `frames_dropped` counter is exposed via debug log only.

### 5.2 Frame buffer

Comptime-parameterized per build:

```zig
pub fn FrameBuffer(comptime cfg: LedConfig) type {
    return struct {
        bytes: [cfg.count * cfg.pixel_format.stride()]u8,
        pub fn setLinear(self: *@This(), i: u32, c: Rgb) void { ... }
        pub fn setXY(self: *@This(), x: u16, y: u16, c: Rgb) void { ... }
        pub fn clear(self: *@This(), c: Rgb) void { ... }
    };
}
```

`LedConfig` fields (all comptime):
- `count: u16` — total pixels.
- `pixel_format` — `rgb | grb | rgbw`.
- `timing_profile` — `ws2812b | ws2814 | ws2815`.
- `layout` — `strip | serpentine{w, h} | panels{...}`.

The layout mapping (`x, y → linear index`) is a `switch` on `cfg.layout` resolved at comptime; zero runtime branching.

The effect boundary is always linear `Rgb` (three floats or three u16s). Pixel-format conversion, gamma, brightness, and channel-order swizzle happen in post-processing.

### 5.3 Post-processing

Applied in this order (order matters):

1. **Solid-color fade blend.** When solid mode (`EffectId=0`) is active and the target color has changed, blend from `render_current` toward the new target over 400 ms. This is what makes Zigbee color control feel non-janky in HA.
2. **Global brightness.** `CurrentLevel / 254` scales linear RGB. Done before gamma so low levels don't crush.
3. **Gamma.** `pow(x, 2.2)` via a 256-entry LUT (comptime-generated).
4. **RGBW split** (WS2814 only). `W = min(R,G,B); R -= W; G -= W; B -= W`.
5. **Channel-order swizzle** (comptime, RGB / GRB).
6. **Identify overlay.** If `Identify.IdentifyTime > 0`, alpha-blend a 2 Hz white flash on top at 50%.
7. **Commissioning hint.** If not joined to a Zigbee network, dim white blink at 1 Hz on LED 0 only (overlaid on the effect).

### 5.4 LED output driver

Uses the ESP32-C6 RMT peripheral in DMA mode. `led_output` is a thin Zig wrapper over `rmt_new_led_strip_encoder` from ESP-IDF's WS2812 example, generalized for timing profiles. On multi-pin builds (multiple strips / panels), each pin gets its own RMT channel; transmits are launched in parallel and awaited before the next frame kick.

Watchdog behavior: if RMT transmit doesn't complete within 8 ms, log a warning, skip the frame, retry next tick. Do not block indefinitely.

## 6. Effect engine and roster

### 6.1 Engine

An effect is:

```zig
pub const Effect = struct {
    name: []const u8,     // stable id string, logged
    layout_kinds: LayoutKindMask,  // which layouts this effect works on
    render: *const fn (
        state: *const EngineState,
        t_ms: u64,
        out: anytype,   // *FrameBuffer(cfg)
    ) void,
};
```

Effects registered in a **comptime table**, append-only. Order defines `EffectId`. A comptime hash of `(name, index)` pairs is emitted as a build artifact and checked into the repo, so accidental reordering surfaces as a build failure.

Effects incompatible with the build's `cfg.layout` are excluded from the registration table entirely. `EffectCount` is therefore comptime per build — a strip build and a matrix build advertise different valid ranges. The Z2M converter uses `EffectCount` to size the dropdown.

Out-of-range `EffectId` writes fall back to `solid`, log at debug, respond `SUCCESS` on the ZCL side (never fail an attribute write on a clamp).

### 6.2 Palettes

Palettes are `[16]Rgb` gradient anchors, comptime tables. `PaletteId=0` is the sentinel meaning "use the commanded color from ColorControl xy". `PaletteId>=1` selects a built-in palette. Effects call `palette.sample(t)` (linear interpolation).

Palette list is comptime; count exposed later as needed.

### 6.3 V1 effect roster (9 effects)

Registered in this order (`EffectId` value in parens):

| Id | Name | Layout | Notes |
|---|---|---|---|
| 0 | `solid` | any | Renders `ColorControl.xy` → linear RGB (via CIE-1931 xy→RGB matrix). Special-cased in post-processing to route through the fade blender. |
| 1 | `breathe` | any | Sine amplitude on commanded color or palette-sampled color. |
| 2 | `comet` | any | Bright head + fading tail traveling along the linear index. Palette-aware. |
| 3 | `wipe` | any | Forward fill, then forward clear, repeating. Direction reversal by `EffectIntensity > 128`. |
| 4 | `sparkle` | any | Random per-pixel twinkles; density scaled by `EffectIntensity`, decay by `EffectSpeed`. |
| 5 | `rainbow` | any | Palette-scroll effect with the `rainbow` palette forced. Equivalent to `comet` with palette=rainbow and different sampling, but shipped as its own effect for HA UX clarity. |
| 6 | `candle` | any | Perlin-noise slow warm flicker. From the Arduino prototype — deep-red-through-amber, saturation pinned, never fully dark. |
| 7 | `fire_1d` | strip | 5 zoned flame simulations (from the Arduino prototype's insight — single long flame reads as a gradient). Pinned to a bespoke `fire` palette; `PaletteId` ignored. |
| 8 | `plasma_2d` | matrix | Perlin-noise driven color field on the matrix grid. Palette-driven. Excluded from strip builds via `layout_kinds`. |

Append-only means: new effects land at ids 9, 10, … . Existing ids are never reused for a different effect.

**Deviation from an earlier draft.** An earlier draft ordered these differently (sparkle=3, wipe=4, fire_1d=5, plasma_2d=6, rainbow=7, candle=8). Ordering was updated to match the shipped registration table in `effect_engine.zig`; the Z2M converter agrees with the shipped order. Recorded in `.superpowers/sdd/2026-08-28-zigled/progress.md`.

## 7. Persistence, boot, error handling

### 7.1 NVS

Single namespace `zigled`, single blob key `state`, with fields:

| Field | Type | Reason |
|---|---|---|
| `on` | `u8` | On/Off restore. |
| `level` | `u8` | Last CurrentLevel. |
| `color_x`, `color_y` | `u16` | Last xy. |
| `effect_id` | `u16` | Last effect. |
| `speed`, `intensity`, `palette` | `u8` | Effect params. |
| `schema` | `u16` | Schema version. Bumped on layout change. |

Not persisted: Zigbee network state (ESP-Zigbee-SDK owns its own NVS namespace), identify countdown, frame counter, `frames_dropped`.

**Debounced writes:** any mutating command sets a `dirty` flag and `deadline = now + 2000 ms`. Each render tick, if `dirty && now >= deadline`, flush all fields in one `nvs_set_blob` → `nvs_commit`. Upper bound: one commit per 2 s regardless of slider speed. No graceful-shutdown flush; the 2 s window is the cost.

### 7.2 Boot sequence

Deterministic, photons-before-radio:

1. `app_main` starts, logging configured, GPIO / RMT / frame buffer allocated.
2. Read NVS `zigled/state` → populate in-memory `state`. Empty NVS or schema mismatch → defaults (`on=true, level=128, effect_id=0, palette=0, color = warm-white xy`).
3. Spawn `render_task` — starts rendering restored state within one frame.
4. Init ESP-Zigbee-SDK, spawn `zigbee_task`, kick commissioning:
   - If NVS shows we were joined → attempt rejoin.
   - Otherwise → permit-join for 180 s; commissioning hint (§5.3.7) is visible in render output.
5. Once joined, restore reporting configs from ESP-Zigbee-SDK's own NVS.

### 7.3 Factory reset

BOOT button on GPIO9 (XIAO_ESP32C6 default). Polled from the render task each tick. Held ≥ 3 s:

1. Fill strip red for 300 ms (user feedback).
2. Erase `zigled` NVS namespace.
3. Call `esp_zb_factory_reset()`, which reboots.

### 7.4 Error handling — three tiers

**Tier 1 — recover at the boundary**, log at warn, continue:
- NVS read fails / schema mismatch → apply defaults.
- ZCL attribute write with out-of-range value → clamp, respond `SUCCESS`.
- Effect id out of range → fall back to `solid`, log once.

**Tier 2 — degrade gracefully**, log per event (rate-limited if bursty):
- RMT transmit timeout → skip frame, retry next tick.
- Command queue full → drop *oldest* command (`xQueueOverwrite`-style pattern), never the newest. Recent intent trumps stale.
- Zigbee stack callback returns error → log, do not re-invoke, keep rendering.

**Tier 3 — hard fail, restart via watchdog**:
- Peripheral init failure at boot (RMT alloc, GPIO conflict).
- Repeated Zigbee stack init failure (3 attempts, exponential backoff).

No silent fallbacks. Every recovery path logs at least once per class-of-event.

## 8. Testing

Three layers.

### 8.1 Host unit tests (`zig build test`)

No hardware; runs on macOS.

- `effect_engine`: render each effect at a fixed timestamp into a stub buffer, compare against golden `.bin` files. Catches accidental visual regressions when tweaking gamma / effect internals.

**V1 deviation from golden-frame testing.** The v1 host tests use behavior asserts (e.g. "some pixels lit", "at least half the pixels warm", "brightness changes across time") instead of golden `.bin` comparisons. Rationale: three effects (`candle`, `sparkle`, `fire_1d`) are RNG-driven and would produce brittle goldens under any change to Zig's stdlib PRNG or seeding; behavior asserts caught real defects during implementation (e.g. Task 6's `.panels` compile bug via a mapping test). Deterministic effects (`solid`, `rainbow`, `wipe` at fixed t) COULD grow golden coverage as a post-v1 hardening step. Deviation recorded in `.superpowers/sdd/2026-08-28-zigled/progress.md`.
- `frame_buffer`: layout mapping for strip, serpentine 8×8, dual 16×16 panels. Set `(x,y)`, assert linear index.
- `post_processing`: brightness × gamma × RGBW split — table-driven, ~30 rows.
- `state`: apply a scripted sequence of `Command`s, assert final `state`. Exercises clamping and mode transitions.
- `persistence`: fake NVS backend (in-memory), assert debouncing and schema-version migration.

### 8.2 Integration tests (host, simulated)

Feed a scripted ZCL command sequence into a mocked `zigbee_iface`, assert the resulting command queue matches expectations. No real Zigbee coordinator involved.

### 8.3 On-device smoke test

`zig build flash-smoke` target: boots, runs each registered effect for 2 s, cycles palettes, exercises identify, exercises BOOT factory reset (dry-run — skips the actual erase behind a build flag). Manual eyeballing; scripted so the sequence is reproducible.

### 8.4 Out of scope for v1

- Hardware-in-the-loop CI.
- End-to-end tests against a real Zigbee coordinator in CI.

## 9. Observability

- `esp_log` per-module tags: `ZIGLED_RENDER`, `ZIGLED_ZB`, `ZIGLED_NVS`, `ZIGLED_STATE`, `ZIGLED_BOOT`.
- Compile-time log level (default `INFO`, `DEBUG` per build).
- Internal counters (log only, no cluster): `frames_dropped`, `queue_high_watermark`, `nvs_writes`.

No diagnostic Zigbee cluster in v1.

## 10. Migration from the Arduino prototype

The existing `zb_ws2815_c6/` firmware and `zb_ws2815.mjs` converter continue to work, unchanged, on devices flashed with them. ZigLED presents a **different** external contract (`Gekkotron / ZigLED-1`, single endpoint, mfg cluster), so a device flashed with ZigLED must be:

1. Re-paired to the Zigbee coordinator (fresh join — no migration of the old three-endpoint state).
2. Configured against the new Z2M converter `gekkotron_zigled.mjs`.

The prototype's `.ino` and `.mjs` files remain in the repo as reference. Fire-zone counts (5), phase-step scaling, and Perlin-noise candle tuning are directly reused in the Zig effect implementations.
